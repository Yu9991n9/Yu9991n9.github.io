HTTP请求走私

简介

在如今很多的网站中都使用http服务链 用户将服务发送到前段服务器 前端服务器进行初步的筛选和处理 再转发到后端的服务器

当前端服务器向后端转发请求时 它会向统一后端发送多个请求 这样可以提高效率 该协议使http请求一个接一个的发送 接受服务器解析的http请求表头以确定这一个请求在哪里结束 下一个请求再哪里开始

这种情况下前段和后端之间必须对请求之间的边界保持一致 否则攻击者就可以发送一个模棱两可的请求 被前端和后端以不同的方式解读

在这里先简要讲解一下请求走私漏洞的成因；

核心原因还是前端和后端关于判断http请求在哪里结束的判断不同 在http当中允许Content-Length也就是CL和Trans-Encoding也就是TE两者同时出现

前端如果按一种规则放行了一个请求 而后端按照另外一种方式提前结束了对请求的读取 那么这时没有被后端读取到的内容就会遗留在后端的内存管道当中 当下一个用户的正常请求到达后端时 刚才的代码就会被拼接进正常请求的开头 这就形成了http请求走私

类型

CL不为0的get请求

下面那个get就是我们塞到请求包里面的东西 我们可以明显看见这里正常的请求包里面是写了CL的 这里的44个包括回车和换行 只是在bp这些软件里面不会显式的显式出来 我们在实操的时候也只需要回车就可以了 但是我们自己写脚本或者在终端里面发爆破就需要把这个写出来了

前端看见CL唯44 往下一读发现我们塞进去的东西刚好长度为44 放行 到了后端 结果后端不认CL 读到第二个get上面的\r和\n就直接以为你这个请求结束了 那么这时候我们塞进去的东西就留在管道pipeline里面了 在现代 HTTP 通信中，为了效率，前端和后端建立起 TCP 连接后，这个连接是不会立刻断开的。如果管道里还有数据，后端会认为：“这是前端发来的下一个全新请求”。

然后就会回头来处理这个数据 这样就实现了请求走私

如果应用程序容易受到该漏洞的CL.TE变体的攻击，则基于时间的TE.CL漏洞测试可能会破坏其他应用程序用户。因此，要隐身并最大程度地减少中断，您应该首先使用CL.TE测试，只有在第一个测试失败的情况下才继续进行TE.CL测试
