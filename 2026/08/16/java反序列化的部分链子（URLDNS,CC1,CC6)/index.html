Java反序列化的部分链子（URLDNS、CC1、CC6）

体上来说 序列化的本质都是为了数据传输 当两个进程进行通信时 就可以通过序列化来来进行传输

之所以会设计这种传输方式一是为了实现数据的持久化 通过序列化可以将数据永久地保存到键盘上 二是实现远程通信

java反序列化和我之前学习的php反序列化不同 php反序列化 php的序列化很明显的一个特征就是{}之类的 但是java原生的序列化数据都是二进制格式的 两者从格式上来说有本质上的区别

java序列化后的数据在十六进制当中很显著的一个特征就是它的数据开头是：

AC ED 00 05

base64编码之后是：rO0AB

java原生序列化

java提供了ObjectOutputStream来封装序列化逻辑 同时我们也要借助java原生的FileOutputStream()来进行操作

我们可以将FileOutputStream()理解为一个向硬件上写文件的管道 但是这个管道只能读懂二进制的内容直接明文传原始内容会报错 那么这时ObjectOutputStream()就登场了 这个类可以将我们传入的数据转换为二进制的内容 那么此时我们的管道就可以运行了

需要注意的点

在反序列化的过程中 它的父类如果没有实现序列化接口 那么将需要提供无参构造函数来重新创建对象

一个实现serializable接口的子类也是可以被序列化的

静态成员变量是不能被序列化的 序列化针对的是对象属性 而静态的成员变量是属于类的

transient标识的对象成员变量不参与序列化 就比如我们在上述例子当中我们把name的属性前面加上一个transient 那么我们序列化后得到的值就是null

可能存在安全漏洞的形式

(1) 入口类的readObject直接调用危险方法 比如可以直接调用Runtime.getRuntime()

(2) 入口参数中包含可控类，该类有危险方法，readObject时调用

(3) 入口类参数中包含可控类，该类又调用其他有危险方法的类，readObject时调用

(4) 构造函数/静态代码块等类加载时隐式执行

原理

这是一个java反序列化漏洞当中相对来说比较简单的一个链子 先直接给链子：

首先我们要来学习HashMap类 这是一个java的内置类 它是一个键值对字典 往里面存东西时 必须以键值对的形式存进去 比如： map.put(恶意URL, “随便什么东西”); 当我们存进去它会执行两个方法 hash和hashcode 其中hashcode()是直接被写在object里面的 换句话说 每个类里面都有hashcode方法 当我们进入到hash这个方法时 它会往下调用到hashcode 然后我们借用反射来进行一些特殊的步骤 这里先不细讲 然后我们就HashMap里塞进了我们的恶意URL 序列化到目标服务器这里主要要让URL扮演key 因为HashMap只会去调用key里面的hashcode（）

当服务器接受到序列化数据时会直接反序列化 但是这里又有一个问题了 不同版本 不同设备下的hash和hashcode计算都可能计算出不同的结果 那假设我们在上一步里面给自己算出来的座位号是8 把数据放进序号为8的座位里了 但是到了服务器这了算出来是9 那它去9里面取那不就报错了 为了防止这种情况 服务器在反序列化HashMap类时 会去调用它的readObject()方法 这个readObject()方法是被重写过的 它重写后的逻辑就是去调用每个key里面的hashcode方法 重新算“座位号” 完整的逻辑应该是readObject去调用putVal 它来执行放置键值对 当它要放置时 会先算出来号码再放 也就是先调用hash() 这时hash就会去让hashcode()先做一遍得到一个数字 但是hashcode()有时可能会出现两个不同数据算出来的值是一样的情况 为了防止这种情况hash再用它的算法再算一遍

这里就有一种特殊情况了当HashMap当中的key是一个URL时 为了计算的准确 服务器会执行一次dns解析去得到真实的ip地址 那么如果我们这里的URL是我们设计好的恶意的网站 那么就可以实现一次攻击了

前置知识

CC是什么

cc的全称叫做Apache Commons Collections 在java当中 程序员需要处理各种集合 就比如上面urldns链当中的HashMap 但是java自带的集合功能又比较基础 于是apache官方就写了一个工具箱 它的名字叫做Common Collection也就是我们所说的cc

InvokerTransformer类

这个类是cc包当中的一个类 在cc当中有一个非常核心的接口叫做Transformer 就和它的名字一样 这个接口的设计理念就是进去一个东西出来另一个东西 那么InvokeTransformer类就是一个我们往里面丢对象 它就会自动去调用这个对象的某个方法 并且把方法的返回值给吐出来

这个有三个核心的参数：

iMethodName、iParamTypes和iArgs 其分别对应方法名 参数类型 具体参数 我们只需要对应赋值就可以实现对某个方法的执行了

  • 使用InvokerTransformer对象调用transform()方法，会以反射的方式执行任意方法。

对上三类的总结

上面的三个类都通过不同的方法来执行transform 并且这三个类都实现了Serializable接口 也就是说他们都可以进行序列化和反序列化

  • 以反射方式执行任意方法
  • 遍历链内部的所有Transformer执行transform()

  • 返回固定值，值为构造方法传入的参数值

  1. 前置准备：擦除本地“走火”指纹 (防哑火机制)

在本地生成恶意序列化数据（Payload）时，我们需要将 TiedMapEntry 作为 Key put 进最外层的 HashMap（即包裹实体）。但这个 put 动作会在本地触发一次底层的 LazyMap.get() 逻辑，导致 LazyMap 内部提前生成并残留一个无害的垃圾数据（假子弹）。 为了防止 Payload 发送给目标后无法触发漏洞，我们在执行序列化之前，必须显式调用 remove() 方法，将这个本地残留的 Key 擦除。这一步至关重要，它保证了受害者在解析时，LazyMap 处于“空状态”，从而必定走进 if (map.containsKey(key) == false) 的代码分支，去“现造”恶意数据。

  1. 漏洞入口：HashMap 的强迫症 (Source)

完成本地清理和序列化后，我们将 Payload 发送给目标服务器进行反序列化。 漏洞的完美触发，得益于 HashMap 自身重写了反序列化入口 readObject() 方法。当 HashMap 在内存中被还原时，它需要重新计算并恢复内部所有键值对的位置（恢复 Hash 表）。为了决定位置，它会自动调用每一个 Key 的 hash() 方法，进而同步触发该 Key 的 hashCode() 方法。这就为我们提供了一个天然且必定执行的攻击入口（Source）。

  1. 完美桥梁：TiedMapEntry 的连带反应 (Bridge)

我们在构造时，精心把一个 TiedMapEntry 对象作为 Key 埋在了外层的 HashMap 中。 当 HashMap 自动调用 TiedMapEntry.hashCode() 时，不可逆的连锁反应开始了：

  • TiedMapEntry 的 hashCode() 方法底层硬编码了调用自身绑定的 getValue() 方法。
  • 而它的 getValue() 方法，又会直接调用其绑定的内部 Map 的 get() 方法。 通过这个“桥梁”，程序原本安全无害的 Hash 计算，被强行扭转成了极其危险的 Map 查询操作。

​ 4.终极引爆：LazyMap 的懒加载机制 (Sink)

由于 TiedMapEntry 内部绑定的正是我们的恶意核心 LazyMap，此时程序的执行流精准来到了 LazyMap.get() 方法。 因为我们在第 1 步已经清空了残留数据，此时满足了内部字典中找不到对应 Key 的条件。LazyMap 的“懒加载”机制被激活，它为了生成这个缺失的数据，直接调用了其内部工厂类的 factory.transform() 方法。 至此，攻击闭环完美形成，提前装填好的 ChainedTransformer 恶意链条被彻底引爆，最终达成任意代码执行（RCE）。
